DESIGN PATTERNS

Design patterns give Intaliq proven solutions to problems that appear across its features. Three patterns carry most of the design: Observer keeps session members informed, Repository isolates every read and write to Supabase behind one interface, and State governs the life cycle of a booking request. Each one is described below with the problem it solves, why it was chosen over the alternatives, and how it is applied in the Intaliq modules.

Selected Design Patterns

NODE // DP-01

Observer

CLASSIFICATION: Behavioural

Problem Statement

When a coach publishes a session announcement or accepts a join request, several parts of the system have to react at once: the member list, the push-notification service (SI-4), the email service (CI-3), and any screen currently showing that session. Calling each one directly from the coach feature would tie session management to every consumer and force a change here for each new reaction.

Selection Rationale

Observer lets the session publish one event that interested parties subscribe to. It suits the requirement that announcements reach all registered members (FR-07) while keeping the coach flow independent of how a member is reached, and it supports modifiability: new subscribers, such as an in-app activity feed, can be added without touching the publisher.

Project Application

The Session module raises events such as announcementPosted, memberAdmitted and requestRejected. The subscribers are the push-notification adapter, the email adapter and the session screens, which refresh the member list and the announcement feed when an event arrives.

Expected Benefits

  • ▹A coach action reaches every member through push and email without the session code knowing about either service.
  • ▹New reactions to session events are added by registering another subscriber.
  • ▹Screens stay in step with the backend because they react to the same events.

NODE // DP-02

Repository

CLASSIFICATION: Structural / Data access

Problem Statement

Sessions, activities, goals, partner requests and chat messages all live in the Supabase database (SI-1), and the app must keep working offline: unsent actions are stored locally and synced when the connection returns (CI-4, CI-5). Scattering Supabase calls through the screens would duplicate that offline logic and make the app hard to test or to move to another backend.

Selection Rationale

A repository gives each entity one interface for reading and writing, with the choice between the local store and the network hidden behind it. It keeps the offline rule in a single place, supports the availability target of no lost activity logs after reconnect, and lets features be tested against a fake repository instead of a live database.

Project Application

SessionRepository, ActivityRepository, GoalRepository and PartnerRepository sit in the infrastructure layer. Each one reads through the Supabase client, writes through the sync queue when the device is offline, and returns the domain entities defined in the data dictionary.

Expected Benefits

  • ▹Offline storage and synchronisation are implemented once, not in every feature.
  • ▹Features depend on an interface, so the backend can change without rewriting them.

NODE // DP-03

State

CLASSIFICATION: Behavioural

Problem Statement

A join request moves through several stages: submitted by the user, reviewed by the coach, then accepted, rejected, or blocked because the session is full or the fitness level does not match (FR-01, FR-06). Expressing this with flags and nested conditions spread across the booking and admission code makes invalid transitions easy to introduce, such as admitting a member into a full session.

Selection Rationale

State turns each stage into its own object that decides which actions are allowed and which stage comes next. The rules from the SRS alternative scenarios live in one place, the same states drive the state machine diagram in the Process View, and the capacity and fitness-level checks cannot be bypassed.

Project Application

A BookingRequest holds a state of Pending, Accepted, Rejected or Cancelled. The admission feature asks the current state to handle accept or reject; the Pending state checks session capacity and the member fitness level before moving to Accepted and raising the notification event.

Expected Benefits

  • ▹Invalid transitions, such as admitting into a full session, are rejected by the state itself.
  • ▹The booking rules are read in one place and match the state machine diagram.
