Architecture / Architectural Style

System Architecture

Intaliq runs as a client–server system: a layered mobile client on iOS and Android talks over HTTPS to a cloud backend that owns authentication and the shared database, with AI, push-notification and email services attached to it. This choice shapes every other view — it decides where session data lives, where capacity and security rules are enforced, and what the app must do when the network drops during an outdoor workout.

Primary Architecture

Client–Server with a Layered Client

> A layered mobile client over HTTPS to a Supabase backend and external services

SEC_02

Description

In a client–server style the system is split between clients that request work and a server that owns the shared data and the rules protecting it. Clients never reach the database directly: every request passes through the server, which authenticates the caller and decides what may be read or written. Inside the client, the layered style stacks presentation, application logic, domain and infrastructure so that each layer only depends on the one beneath it.

Intaliq has three tiers. The mobile client holds the screens, the use-case logic and a local store for unsent actions. The backend — Supabase — provides authentication and the PostgreSQL database for users, coaches, sessions, goals, activities and partner requests (SI-1, SI-3). A third tier of external services covers AI advice, push notifications and email (SI-2, SI-4, CI-3). The connector between them is HTTPS (CI-1) over Wi-Fi or mobile data (CI-2), and the client–server boundary is where authentication, capacity and fitness-level checks are enforced.

SEC_03

Why Selected

The style follows from what Intaliq has to do: many users and coaches share the same session data from their own phones, and that data must stay consistent and protected.
  • Shared, consistent data: session capacity, member lists and announcements have one authoritative copy on the server, so two users cannot take the last place in a session (FR-06), and it supports 99% availability with many simultaneous users (REL-1, AVA-1).
  • Security in one place: authentication before any personal data is transmitted, HTTPS transport and password rules are enforced at the server boundary rather than in each screen (CI-1, CI-7, SEC-1, SEC-2).
  • Fits the team and the roadmap: it keeps the prototype stack of Vite, Supabase, GitHub and Vercel that the team already knows, and leaves room for the planned map integration, AI partner matching and wearable devices (SI-5, HI-1) as further services behind the same boundary.
SEC_04

Application to System

The client holds the Sessions, Activities, Goals, Partners and AI Chatbox features on top of the domain entities and an infrastructure layer with the Supabase client and the offline queue. The server holds the tables and access rules for those entities. Booking is the clearest example: the app submits a join request, the server checks capacity and fitness level, stores the decision and triggers the notification services, and the app shows the result — or queues it locally if the phone is offline (CI-4, CI-5).

SEC_05

Advantages

One source of truthSessions, capacity and member lists live on the server, so coaches and users always see the same state and bookings cannot exceed capacity.
Security at one boundaryAuthentication, authorization and HTTPS are enforced where the client meets the server, so personal data and activity history are never exposed to an unauthenticated caller.
Independent evolutionThe layered client can be redesigned — as the usability findings require — and services such as maps or AI matching can be added without changing the data model on the server.
SEC_06

Trade-offs & Limitations

Dependence on connectivityOutdoor workouts happen where coverage is weak, so the client needs a local store and a sync queue to avoid losing activity logs (CI-5) — extra logic that a purely online design would not need.
The backend is a single point of failureIf Supabase or the network is down, booking, admission and announcements all stop, which puts pressure on the 99% availability target and makes backups and monitoring necessary.
Round trips cost timeEvery list and statistic is a network call, so the 3-second and 4-second response targets (PER-1, PER-2) depend on caching and careful queries rather than on local computation.
