SAD § 1.2 · Purpose

Make running, cycling and hiking accessible and enjoyable

Intaliq is a mobile fitness app. Users track daily activity, set goals and join group sessions held daily by a trained team of coaches, through a simple design that makes outdoor activity feel less intimidating.

01

Easy navigation

Guide users through outdoor activities in Saudi Arabia with an easy-to-use interface.

02

Accurate tracking

Provide reliable tools for monitoring activity and setting activity goals.

03

Social connection

Connect people across Saudi Arabia who share an interest in outdoor activity.

D2 § 3.1 · 3.3 · Architectural Style

Client–server, with a central backend

The mobile app is the client. One backend handles authentication, business logic and every call to the database and the AI service.

D2 § 3.2 · 3.3 · Justification & Communication

Why this style fits Intaliq

Data centralization

Users, actions, goals and sessions controlled through one backend and database.

Security

Authentication and authorization enforced on the server.

Maintainability

App and backend evolve independently.

Performance

Heavy processing stays on the server; the app focuses on the user.

Integration

Clean exchange with third-party services such as the AI chatbox.

Communication process
  1. User performs an action in the mobile app
  2. App sends the request to the backend over HTTPS
  3. Backend authenticates and processes it
  4. Backend calls the database or AI service if needed
  5. Backend returns the outcome to the app
  6. App shows the result to the user

DP-01 · Observer · Behavioural

One coach action, every member informed

Problem

Announcements and admissions must reach the member list, push, email and open screens at once. Calling each directly ties session code to every consumer.

Why Observer

The session publishes one event; subscribers react. Announcements reach all members (FR-07) and new reactions need no change to the publisher.

In Intaliq

announcementPosted · memberAdmitted · requestRejected

DP-02 · Repository · Structural / Data Access

One door to the data, online or offline

Problem

All data lives in Supabase and unsent actions must sync later. Scattering database calls through screens duplicates the offline logic and blocks testing.

Why Repository

Each entity gets one read/write interface that hides whether data comes from the local store or the network — so no activity log is lost after reconnecting.

In Intaliq

SessionRepository · ActivityRepository · GoalRepository · PartnerRepository

DP-03 · State · Behavioural

Booking rules that can't be bypassed

Problem

A join request is submitted, reviewed, then accepted, rejected or blocked (FR-01, FR-06). Flags and nested conditions make invalid moves — like admitting into a full session — easy.

Why State

Each stage is an object that decides which actions are allowed and what comes next. The SRS rules live in one place and match the Process View.

In Intaliq

Pending checks capacity and fitness level before moving to Accepted and raising the notification event.
