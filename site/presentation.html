SAD 1.2 · Purpose

Make running, cycling and hiking accessible and enjoyable

Intaliq is a mobile fitness app. Users track daily activity, set goals and join group sessions held daily by a trained team of coaches, through a simple design that makes outdoor activity feel less intimidating.

D2 3.1 & 3.3 · Architectural Style

Client–server, with a central backend

The mobile app is the client. One backend handles authentication, business logic and every call to the database and the AI service.

D2 3.2 & 3.3 · Justification & Communication

Why this style fits Intaliq

Data centralization

Users, actions, goals and sessions controlled through one backend and database.

Security

Authentication and authorization enforced on the server.

Maintainability

App and backend evolve independently.

Performance

Heavy processing stays on the server; the app focuses on the user.

Integration

Clean exchange with third-party services such as the AI chatbox.

Communication process
  1. User performs an action in the mobile app
  2. App sends the request to the backend over HTTPS
  3. Backend authenticates and processes it
  4. Backend calls the database or AI service if needed
  5. Backend returns the outcome to the app
  6. App shows the result to the user

SDD 2.4 – 2.6 · Architectural Viewpoints

Inside the client, and inside the server

View shows screens, Controller handles actions, Model holds data and calls the backend API — easier to maintain, extend and test.

Each layer talks only to its neighbour, so changes stay local, the database is reached only through the layers above it, and each layer is tested alone.

SDD 3.1 · Detailed Design

Three Gang of Four patterns, one of each kind

DP-01 · Factory Method · Creational

One logging process, any activity

How it's applied

RunningLogger, HikingLogger and CyclingLogger each override createActivity(). Pick hiking, and the HikingLogger builds a HikingActivity that the logging process uses without knowing its type.

Why Factory Method

Every activity is validated and saved the same way but counts calories differently. A new sport such as padel only needs its own logger and activity class — nothing else changes.

DP-02 · Observer · Behavioural

One change, everyone informed

How it's applied

SessionService is the subject; UserNotification and ReminderService observe it. When a class is cancelled, each observer reacts on its own — one alerts the user, the other reschedules reminders.

Why Observer

Announcements reach every admitted member, and booking decisions reach the requester (Book a Session). Session never handles delivery, so new channels such as email plug in without changing it.

DP-03 · Adapter · Structural

Any AI provider, one interface

How it's applied

ChatboxService only calls AIChatService.sendMessage(). AIServiceAdapter converts the question into the external service's format, sends it over HTTPS, and converts the answer back.

Why Adapter

Provider-specific formats stay out of the chatbox logic. If the external API changes, only the adapter changes; switching provider means writing a new adapter.
